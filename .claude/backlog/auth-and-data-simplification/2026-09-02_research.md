# Research: Auth & Data Layer Simplification (web)

> **One-line thesis:** The webapp maintains a hand-rolled second copy of both
> the session and the entire dataset alongside what Supabase already provides.
> Collapse the webapp onto Supabase as the single source of truth, cache only
> auth tokens, and let the planned **Flutter iOS/Android apps own true offline
> support**. This is a net _deletion_ of code.

**Scope decision driver (Eric, 2026-09-02):** The IndexedDB/Dexie offline-first
mirror originally existed so the webapp kept working in crowded venues / band
basements with no signal. With native Flutter apps now planned for iOS+Android,
that offline burden moves to the native clients. The webapp should simplify to
"online app that talks to Supabase directly + caches auth tokens only."

---

## 1. Current state — two parallel truth systems

### 1a. Session (the auth clunk you already feel)

Supabase's SDK is already a complete session manager. `src/services/supabase/client.ts:24-26`:

```ts
auth: { autoRefreshToken: true, persistSession: true, detectSessionInUrl: true }
```

It persists to `sb-*` localStorage keys, silently refreshes tokens, and emits
`onAuthStateChange` (SIGNED_IN / SIGNED_OUT / TOKEN_REFRESHED). That is the
authoritative session.

Layered on top is a hand-rolled mirror + several redundant expiry detectors:

| Mechanism                                 | Location                                    | What it duplicates           |
| ----------------------------------------- | ------------------------------------------- | ---------------------------- |
| `rock_on_session` copy w/ own `expiresAt` | `SessionManager.ts:3,34,104`                | the `sb-*` token + expiry    |
| `rock_on_offline_session` 30-day copy     | `SessionManager.ts:4,49-91`                 | (unused by the guard — dead) |
| 1.5h grace period                         | `useAuthCheck.ts:10,146-171`                | offline tolerance            |
| 30s polling `setInterval`                 | `AuthContext.tsx:149`                       | expiry detection             |
| `visibilitychange` re-check               | `AuthContext.tsx:162`                       | expiry detection             |
| custom `auth-logout` event bus            | `AuthContext.tsx:742`, `useAuthCheck.ts:89` | SIGNED_OUT                   |
| cross-tab `storage` listener (x2)         | `AuthContext.tsx:174`, `useAuthCheck.ts:84` | multi-tab sync               |

**Blast radius:** `SessionManager` is imported by only **3 files**
(`AuthContext.tsx`, `useAuthCheck.ts`, itself). Small and safe to excise.

**Bugs this causes (verified in the read-only assessment):**

1. **"Session invalid" for ordinary inactivity.** On reload/nav,
   `SessionManager.loadSession()` auto-nulls an expired session
   (`SessionManager.ts:34-37`); the guard then reads `!session` and reports
   `session-invalid` (`useAuthCheck.ts:131-141`), which `AuthPages.tsx:1853`
   renders as _"Your session was invalid. Please log in again."_ The benign
   idle-logout is indistinguishable from real corruption, and the reload path
   (the common one) always hits "invalid," never "expired."
2. **Grace period is effectively dead code.** The grace branch
   (`useAuthCheck.ts:146-171`) only runs for a _non-null but expired_ session,
   but `loadSession()` and `isSessionValid()` share the same `expiresAt < now`
   boundary — so whenever `isSessionValid` is false, `loadSession` already
   returned null. Unit tests hide this by mocking the two methods independently
   (`useAuthCheck.test.tsx:158-163`) → false green. The advertised
   "1.5h offline gig grace" doesn't function through the guard on reload.
3. **Blank page while unauthenticated.** Two paths:
   (a) mirror says valid but the Supabase token is actually dead (refresh
   failed: password change, revocation, clock skew) — guard authorizes off the
   mirror, RLS queries return empty/401, nothing sets `sessionExpired` because
   the 30s interval only starts once `session` state is populated
   (`AuthContext.tsx:111-112`) → blank, no redirect;
   (b) the guard gates on `currentUserId` alone, but pages render from
   `AuthContext.currentUser`/`currentBand`, populated by `loadUserData`, whose
   errors are swallowed (`AuthContext.tsx:608-610`) → guard happy, data null,
   blank.

The missing invariant: **"authenticated" should mean "Supabase holds a live
token AND user context is loaded"** — today it means "a localStorage mirror
looked valid."

### 1b. Data (the larger half)

The offline-first data layer mirrors _all_ app data into IndexedDB and reconciles
via a sync queue:

- `src/services/data/` — `SyncEngine.ts` (1,840), `RemoteRepository.ts` (1,911),
  `RealtimeManager.ts` (1,229), `SyncRepository.ts` (901), `LocalRepository.ts`
  (735), contract/factory/types. **~7,165 LOC total.**
- The `RepositoryFactory` always returns the offline-first `SyncRepository`
  (`RepositoryFactory.ts:16-17`) — there is already a seam for swapping impls.
- **Blast radius:** **42 files** import the Dexie `db` directly; **19** import
  the repository. Plus the guardrail apparatus (ESLint `no-restricted-syntax`,
  `tests/unit/guardrails/db-direct-write.test.ts`, `KNOWN_VIOLATIONS`) exists
  _entirely_ to police direct `db.*` writes — remove the local write path and
  the guardrail's reason for existing largely goes away.

## 2. Proposed target design

**Principle:** Supabase SDK = single source of truth for both session and data
on the web. Cache **auth tokens only** (the SDK's own `sb-*` keys). No durable
data mirror on web. Flutter apps carry offline support.

### Phase 1 — Session simplification (ready now, M, low risk)

- **Delete** the `SessionManager` mirror, the 1.5h grace period, the 30s
  polling interval, one of the two `storage` listeners, and the custom
  `auth-logout` bus.
- **Derive** all auth state reactively from `supabase.auth.onAuthStateChange`
  (SIGNED_IN / SIGNED_OUT / TOKEN_REFRESHED) + `getSession()`.
- **Route guard invariant:** authenticated ⇔ `getSession()` returns a live
  session AND user context loaded; on any `loadUserData` failure, redirect (not
  blank).
- **Proactive refresh** on focus/route-change for near-expiry tokens via the
  already-present-but-unused `refreshSession()` (`SupabaseAuthService.ts:424`),
  closing the blank-page window.
- **Messaging split** — distinguish, with honest copy:
  - signed out for inactivity / expiry → _"You've been signed out due to
    inactivity. Please sign in again."_ (info, expected)
  - genuine session error/corruption → a distinct error message (rare)
  - This directly fixes your "always says invalid" complaint.

Phase 1 is **independent of Flutter** and can ship immediately. It is a net code
reduction and fixes all three bugs above.

### Phase 2 — Data-layer removal (gated on Flutter apps existing, XL, high risk)

- Replace `SyncRepository` behind `RepositoryFactory` with a thin
  direct-to-Supabase repository (the factory seam already supports this).
- Remove IndexedDB/Dexie mirror, `SyncEngine`, `RealtimeManager` local merge,
  sync queue. Keep Supabase Realtime subscriptions as _live_ updates (no local
  reconciliation).
- Migrate the **42** `db.*`-importing files to the repository interface; retire
  the `db-direct-write` guardrail + `KNOWN_VIOLATIONS` once the local write path
  is gone.
- Decide web offline behavior (see §4 open question).

**Do NOT start Phase 2 until the Flutter apps are real enough to own offline** —
otherwise you remove venue/basement resilience with no replacement.

---

## 3. Why this fits the codebase

- **Simplicity-first (CLAUDE.md):** both phases _delete_ more than they add.
  Phase 1 alone removes ~4 redundant expiry detectors and a whole mirror class.
- **The `RepositoryFactory` seam already exists** for swapping the data impl —
  the architecture anticipated this.
- **`IAuthService` already exposes `refreshSession` and `onAuthStateChange`** —
  the reactive path is available; the app just doesn't use it as the authority.

## 4. Open questions (for grill-me)

1. **SCOPE — how far does this feature go?**
   - (A) Phase 1 only now, Phase 2 later as a separate release (recommended).
   - (B) One doc, both phases, Phase 2 explicitly gated on Flutter.
   - (C) Auth-only, keep the Dexie data layer indefinitely.
     _Recommendation: (B) — document both, ship Phase 1, gate Phase 2._
2. **Web offline behavior after Phase 2:** hard online-only with a clear
   "you're offline" state (simplest) vs. lightweight in-memory/React-Query
   caching so brief blips don't blank the screen (no durable IndexedDB).
   _Recommendation: React-Query-style ephemeral cache — kills the blank-screen
   failure mode without reintroducing a sync engine._
3. **Realtime:** keep Supabase Realtime as live push updates on web after
   Phase 2, or poll/refetch? (Realtime without a local merge layer is much
   simpler than today's `RealtimeManager`.)
4. **Flutter data layer:** shared contract with web (same repository interface
   shape) or independent? Affects whether Phase 2's thin repo is designed for
   reuse.
5. **Migration safety:** Phase 2 is a 42-file change touching every data path —
   does it wait on the `ci-cd deploy + migration-safety` backlog item landing
   first (it should)?
