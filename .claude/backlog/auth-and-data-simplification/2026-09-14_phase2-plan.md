# Phase 2 Plan — Rip out the sync engine + IndexedDB mirror (web = naive client)

> **Thesis:** The web app becomes a naive online client that reads/writes
> Supabase directly. No durable local mirror, no sync queue, no local merge.
> Live updates come from a single per-band Supabase Realtime subscription on
> `audit_log` (push → invalidate → refetch). Brief network blips are covered by
> an **ephemeral in-memory cache only**. True offline is deferred to the future
> Flutter apps (not built yet — accepted, per Eric 2026-09-14).

This is the biggest backend change to date. Delivered as **one feature branch,
one meaningful release** (Eric: "band-aid moment; multiple small PRs buy us
nothing").

---

## 1. Decisions locked (Eric, 2026-09-14)

1. **Web offline:** ephemeral in-memory cache only. Payloads are small. No
   durable IndexedDB.
2. **Change propagation:** Realtime as **push** — Option A, subscribe to
   `audit_log` (unifies "event log of what changed" + "how sessions learn to
   refetch" into one mechanism). No local merge; push just invalidates and the
   hook refetches from Supabase.
3. **Delivery:** single branch, single release-gated PR.
4. **Flutter gating:** proceed now. Web offline is not a real use case for the
   current handful of users; removing it is a net complexity win. Flutter +
   offline targeted alongside v1.0 (end of year).

## 3. Target design

- `RepositoryFactory` returns `RemoteRepository` (rename/retire `SyncRepository`).
- One repository interface, direct to Supabase. Reads may be wrapped by the
  ephemeral cache (§7-C). Writes go straight to Supabase and return the row.
- `RealtimeManager` **slimmed to a pure notifier**: keep the per-band
  `audit_log` channel, the `*:changed {bandId, action, recordId, userId}`
  emits, toast batching, and own-change skip. **Delete** the audit→model mapping
  (`auditMappers.ts`) and every IndexedDB write (`handleRecordUpsert/Delete`).
  Consumers already ignore those writes (they refetch on the event) — verified
  in `useSongs`/`useRealtimeSync`.
- Dexie/`db` + `LocalRepository` + `SyncEngine` + sync tables deleted.
- Guardrail test + ESLint rule + `KNOWN_VIOLATIONS` deleted.

## 5. Change-feed / audit-trigger extension (Option A)

- Today `audit_log` triggers cover **only** songs, setlists, shows,
  practice*sessions (verified: no later migration adds more). `jam*\*` are
  online-only already.
- New idempotent migration adds `log_audit_trail` AFTER INSERT/UPDATE/DELETE
  triggers to the collaboration tables that matter for live multi-member
  editing. **Proposed set (confirm in grill §7-E):** `bands`,
  `band_memberships`, `song_castings`, `song_assignments`,
  `member_capabilities`. Left as refetch-on-navigation (no live trigger):
  tunings, friends, events, notifications, notes.
- Verify `audit_log` realtime publication already covers new rows (baseline
  enabled realtime on the table, so new triggers flow through the same channel).
- Migration must be idempotent (`DROP TRIGGER IF EXISTS` before `CREATE`), and
  is release-gated (a schema-touching migration in the PR).

## 7. DECISIONS (grill Round 1 settled 2026-09-14)

- **7-A — Repository seam:** migrate ALL callers to the single `repository`
  singleton; retire `getSyncRepository()`. ✓ Eric.
- **7-C — Ephemeral cache:** adopt `@tanstack/react-query`. Realtime push →
  `queryClient.invalidateQueries`. Hooks refactor to `useQuery`. ✓ Eric.
- **7-D — Per-item sync badges:** remove `useItemSyncStatus` and all
  synced/pending indicators entirely (no queue ⇒ nothing pending). ✓ Eric.
- **7-E — Audit triggers:** extend to bands, band_memberships, song_castings,
  song_assignments, member_capabilities (consolidate — one migration). Others
  stay refetch-on-nav. ✓ Eric.
- **7-F — DevDashboard:** **remove the entire DevDashboard** (`src/pages/
DevDashboard/*`, the lazy import + `/dev/dashboard` route in App.tsx),
  `debugSync`, `debugRealtime`. Supabase Studio already gives realtime DB
  views. `/dev/ui-preview` (`DevUIPreviewPage`, non-data) left intact. No e2e
  references it — clean removal. ✓ Eric.

### 7-B — OWN-WRITE REFLECTION (crux, settled 2026-09-14) ✓ Eric

Realtime skips own-changes, so a user's own write reflects via an **optimistic
TanStack Query mutation**:

- `onMutate`: patch the query cache immediately (instant UI = the "it worked"
  signal).
- `onError`: roll back the cache + show a clear failure toast ("Couldn't save —
  check your connection"), so the revert never reads as a random glitch.
- `onSettled`: `invalidateQueries` → refetch to reconcile with the server.
- Realtime continues to skip own-changes (no echo/flicker).

**Confirmation policy: (a) silent success + error-only toast.** No "Saved"
toast on success — the optimistic update is the confirmation. Toasts fire only
on failure. If heavyweight-action reassurance is wanted later, option (c)
(toast only on song/show/setlist create+delete) is a trivial additive
follow-up. Not doing (b) blanket success toasts (noisy for rapid edits like
setlist reorder / confidence taps).

## 8. Effort / risk

XL, high blast radius (36 files + schema + guardrail). Mitigations: the factory
seam + a complete `RemoteRepository` already exist; consumer hooks already treat
realtime as pure invalidate/refetch; migration is mostly deletion. Main risk is
losing a correctness fix currently encoded in `SyncRepository`'s cloud-first
routing (§6 regression watch).
